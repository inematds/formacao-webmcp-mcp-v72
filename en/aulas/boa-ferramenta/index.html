Lesson 3 · 20 min

Designing a good tool: name, description, JSON Schema, idempotency, read-only × with consequences

The model picks the tool by reading its name, description, and schema. The client decides whether to ask for approval by reading the annotations. A badly designed tool gets called at the wrong time or with the wrong argument. In this lesson, you use a script to check that your tools say what they do and what they change.

Start the lesson

In this lesson you will

  1. 1One intent per tool, with a name and description that state it
  2. 2An input schema that rejects the wrong argument before your code runs
  3. 3The four annotations, and the default when you say nothing
  4. 4Text and structured results; an error the model can read

Goal: write the name, description, schema, and annotations that let the agent choose correctly and let the client ask for confirmation when there are consequences.

02 · Annotations: what saying nothing means

The specification's defaults apply when you omit the annotation.

1. readOnlyHint

true = the tool doesn't change the environment. A host can approve a read-only tool on its own.

Without the annotation, the client should assume it changes something.

2. destructiveHint

Only makes sense when the tool is not read-only. true = can delete or overwrite; false = only adds (like a new booking).

If you leave it out on a tool that changes something, the client treats it as destructive.

3. idempotentHint

true = repeating the call with the same arguments has no extra effect. It matters because clients retry calls (the network dropped, MRTR in lesson 5).

reservar_vaga is not idempotent: two calls, two seats.

4. openWorldHint

true = talks to the outside world (web search, third-party API). false = closed domain, like the kit's in-memory catalog.

An open-world tool is an entry point for untrusted content: course 4 covers this.

04 · Check the design with a script

Lists the tools, checks the description and annotation, calls with a good argument and with a bad one.

Terminal · check the tools
cd ~/projetos/formacao-webmcp-mcp-v72/kit
node teste-ferramentas.mjs; echo "saída: $?"
File · kit/teste-ferramentas.mjs
// teste-ferramentas.mjs — checks the tools' design: annotations, valid argument,
// invalid argument (the SDK rejects it before your code runs) and structured result.
import { Client, StreamableHTTPClientTransport } from '@modelcontextprotocol/client';
import { createMcpHandler } from '@modelcontextprotocol/server';
import { createServer } from './servidor.mjs';

const handler = createMcpHandler(createServer);
const cliente = new Client({ name: 'teste-ferramentas', version: '1.0.0' }, { versionNegotiation: { mode: 'auto' } });
await cliente.connect(new StreamableHTTPClientTransport(new URL('http://teste.local/mcp'),
  { fetch: (url, init) => handler.fetch(new Request(url, init)) }));

let falhas = 0;
const confere = (ok, msg) => { console.log(`${ok ? 'ok   ' : 'FALHA'} ${msg}`); if (!ok) falhas++; };

const { tools } = await cliente.listTools();
for (const t of tools) {
  confere(t.description?.length >= 20, `${t.name}: descrição com 20+ caracteres`);
  confere(typeof t.annotations?.readOnlyHint === 'boolean', `${t.name}: diz se é só leitura`);
}
const ok = await cliente.callTool({ name: 'buscar_turmas', arguments: { termo: 'mcp', limite: 1 } });
confere(ok.structuredContent?.turmas?.length === 1, 'buscar_turmas devolve structuredContent com 1 turma');
const ruim = await cliente.callTool({ name: 'buscar_turmas', arguments: { termo: 'm' } });
confere(ruim.isError === true, `argumento inválido vira isError: ${ruim.content[0].text.slice(0, 70)}…`);

console.log(`${falhas} falhas`);
await cliente.close();
await handler.close();
process.exitCode = falhas ? 1 : 0;
