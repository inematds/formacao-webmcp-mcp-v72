Clase 3 · 20 min

Diseñar una buena tool: nombre, descripción, JSON Schema, idempotencia, solo lectura × con consecuencia

El modelo elige la tool leyendo el nombre, la descripción y el esquema; el cliente decide si pide aprobación leyendo las anotaciones. Una tool mal diseñada se llama en el momento equivocado o con el argumento equivocado. En esta clase compruebas, con un script, si tus tools dicen lo que hacen y lo que cambian.

Comenzar la lección

En esta lección vas a

  1. 1Una intención por tool, con un nombre y una descripción que la expresen
  2. 2Esquema de entrada que rechaza el argumento equivocado antes de tu código
  3. 3Las cuatro anotaciones y el valor por defecto cuando no dices nada
  4. 4Resultado en texto y estructurado; un error que el modelo pueda leer

Objetivo: escribir nombre, descripción, esquema y anotaciones que dejen al agente elegir bien y al cliente pedir confirmación cuando hay consecuencia.

02 · Anotaciones: qué significa no decir nada

Los valores por defecto de la especificación valen cuando omites la anotación.

1. readOnlyHint

true = la tool no cambia el entorno. Un host puede aprobar solo una tool de solo lectura.

Sin la anotación, el cliente debe suponer que cambia algo.

2. destructiveHint

Solo tiene sentido cuando no es de solo lectura. true = puede borrar o sobrescribir; false = solo agrega (como una reserva nueva).

Omitirlo en una tool que cambia algo = el cliente la trata como destructiva.

3. idempotentHint

true = repetir con los mismos argumentos no tiene efecto extra. Importa porque los clientes repiten llamadas (se cayó la red, MRTR en la clase 5).

reservar_vaga no es idempotente: dos llamadas, dos plazas.

4. openWorldHint

true = habla con el mundo externo (búsqueda en la web, API de terceros). false = dominio cerrado, como el catálogo en memoria del kit.

Una tool de mundo abierto es una puerta de entrada de contenido no confiable: el curso 4 trata ese tema.

04 · Comprueba el diseño con un script

Lista las tools, comprueba la descripción y la anotación, y llama con un argumento bueno y con uno malo.

Terminal · comprobar tools

node teste-ferramentas.mjs; echo "saída: $?"
Archivo · kit/teste-ferramentas.mjs
// teste-ferramentas.mjs — comprueba el diseño de las tools: anotaciones, argumento válido,
// argumento inválido (el SDK lo rechaza antes de que corra tu código) y resultado estructurado.
import { Client, StreamableHTTPClientTransport } from '@modelcontextprotocol/client';
import { createMcpHandler } from '@modelcontextprotocol/server';
import { createServer } from './servidor.mjs';

const handler = createMcpHandler(createServer);
const cliente = new Client({ name: 'teste-ferramentas', version: '1.0.0' }, { versionNegotiation: { mode: 'auto' } });
await cliente.connect(new StreamableHTTPClientTransport(new URL('http://teste.local/mcp'),
  { fetch: (url, init) => handler.fetch(new Request(url, init)) }));

let falhas = 0;
const confere = (ok, msg) => { console.log(`${ok ? 'ok   ' : 'FALHA'} ${msg}`); if (!ok) falhas++; };

const { tools } = await cliente.listTools();
for (const t of tools) {
  confere(t.description?.length >= 20, `${t.name}: descrição com 20+ caracteres`);
  confere(typeof t.annotations?.readOnlyHint === 'boolean', `${t.name}: diz se é só leitura`);
}
const ok = await cliente.callTool({ name: 'buscar_turmas', arguments: { termo: 'mcp', limite: 1 } });
confere(ok.structuredContent?.turmas?.length === 1, 'buscar_turmas devolve structuredContent com 1 turma');
const ruim = await cliente.callTool({ name: 'buscar_turmas', arguments: { termo: 'm' } });
confere(ruim.isError === true, `argumento inválido vira isError: ${ruim.content[0].text.slice(0, 70)}…`);

console.log(`${falhas} falhas`);
await cliente.close();
await handler.close();
process.exitCode = falhas ? 1 : 0;

ok    reservar_vaga: descrição com 20+ caracteres

El termo "m" tiene 1 carácter y el esquema pide 2: el SDK lo rechazó y devolvió el mensaje como resultado con isError, que el modelo lee y corrige.
